1. Architecture Overview

Strategy: Database-Per-Tenant

Each tenant gets its own MySQL database, completely isolated from other tenants. When a request comes in with X-Tenant-ID: apollo_clinic, the system connects to clinic_tenant_apollo_clinic_db — a separate database with its own tables, data, and MySQL user.

4. Flow 1: Creating a New Tenant (Provisioning)

This is what happens when a Super Admin calls POST /api/super-admin/tenants:

1
TenantController.store() validates input (tenant_code format, plan name, email) and calls the provisioning service.
2
TenantProvisioningService.provision() generates DB credentials: 
$dbName = "clinic_tenant_{$tenantCode}_db";   // e.g. clinic_tenant_apollo_clinic_db
$dbUser = "clinic_{$tenantCode}";              // e.g. clinic_apollo_clinic
$dbPass = bin2hex(random_bytes(24));           // Random 48-char hex password
3
createDatabase() — Creates the MySQL database: 
CREATE DATABASE IF NOT EXISTS `clinic_tenant_apollo_clinic_db`
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci
4
createDatabaseUser() — Creates a dedicated MySQL user with limited permissions: 
CREATE USER 'clinic_apollo_clinic'@'%' IDENTIFIED BY 'random_password';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, INDEX, ALTER
  ON `clinic_tenant_apollo_clinic_db`.* TO 'clinic_apollo_clinic'@'%';
-- Note: No DROP, no GRANT — tenant user cannot destroy data or escalate
5
runTenantSchema() — Creates all 10 tables inside the new database. The schema is defined in getInlineSchema() method which returns CREATE TABLE statements for: roles, users, patients, appointments, appointment_notes, prescriptions, invoices, audit_log, user_sessions, staff.
6
seedTenantDefaults() — Inserts 6 default roles: 
INSERT INTO roles (id, role_name, name) VALUES
  (1, 'Admin'), (2, 'Provider'), (3, 'Nurse'),
  (4, 'Patient'), (5, 'Pharmacist'), (6, 'Receptionist');
7
createInitialTenantAdmin() — Creates the first admin user with a random password (bcrypt-hashed). Returns the plain password to the Super Admin.
8
Register in master DB — Inserts a row into clinic_master_db.tenants with the DB credentials (host, name, username, password), plan, and subscription dates.
⚠️ Rollback on Failure

If any step fails, the service automatically cleans up by running DROP DATABASE and DROP USER to prevent orphaned resources.

5. Flow 2: How a Tenant API Request Gets Routed

This is what happens when a tenant user calls any endpoint (e.g., GET /api/patients):

1
Route Definition — In routes/api.php, every tenant route group includes the $tenant middleware: 
$tenant = ResolveTenant::class;

$router->group([
  'prefix'     => '/api/patients',
  'middleware' => [$tenant, $auth]   // ← ResolveTenant runs first
], function($router) { ... });
2
ResolveTenant.handle() reads the X-Tenant-ID header: 
$tenantCode = $request->getHeader('x-tenant-id');   // "apollo_clinic"
3
Queries master DB for the tenant's DB credentials: 
$tenant = $masterDb->fetch(
  'SELECT id, status, db_host, db_name, db_username, db_password
   FROM tenants WHERE tenant_code = :code',
  ['code' => $tenantCode]
);
4
Validates the tenant:
  • Status must be "active" (not suspended/terminated)
  • Subscription must not be expired
5
Creates PDO connection to the tenant's own database: 
TenantDatabase::getInstance($tenantCode, [
  'db_host' => $tenant['db_host'],
  'db_name' => $tenant['db_name'],     // "clinic_tenant_apollo_clinic_db"
  'db_username' => $tenant['db_username'],
  'db_password' => $tenant['db_password'],
]);
6
Registers the active tenant globally: 
TenantRegistry::set($tenantCode);   // Stores "apollo_clinic" in static var
$request->setAttribute('tenant_id', $tenant['id']);
7
Models use tenant_db() helper — Every model calls this to get the correct PDO: 
// Helpers/functions.php
function tenant_db(): TenantDatabase {
  $code = TenantRegistry::getCode();           // "apollo_clinic"
  return TenantDatabase::getInstance($code);  // Returns cached PDO
}

// Every model follows this pattern:
class PatientModel {
  private function db() { return tenant_db(); }
  
  public function getAll() {
    return $this->db()->fetchAll('SELECT * FROM patients');
    // ↑ Runs against clinic_tenant_apollo_clinic_db.patients
  }
}

Security Layers

LayerWhat It DoesFile : Line
Header validationRejects requests without X-Tenant-IDResolveTenant.php : 17
Master DB lookupValidates tenant exists and is activeResolveTenant.php : 23
Status checkBlocks suspended/terminated/inactive tenantsResolveTenant.php : 36
Subscription checkBlocks expired subscriptions (402)ResolveTenant.php : 47
Separate PDOEach tenant gets its own PDO instanceTenantDatabase.php : 29
Separate MySQL userEach tenant's DB user can only access its own DBTenantProvisioningService.php : 192
Singleton cachingOne PDO per tenant per request (no cross-contamination)TenantDatabase.php : 47

Why Tenant A Can NEVER See Tenant B's Data

  1. Different databases — Apollo's patients are in clinic_tenant_apollo_clinic_db.patients, XYZ's are in clinic_tenant_xyz_hospital_db.patients
  2. Different MySQL users — clinic_apollo_clinic user has GRANT only on clinic_tenant_apollo_clinic_db.*
  3. Different PDO connections — PHP creates a separate PDO object for each tenant
  4. No cross-DB queries — Models use tenant_db() which always resolves to the current request's tenant

③ MasterDatabase.php — Master DB Connection

Located at: app/Core/MasterDatabase.php

  • Singleton — one instance for the entire application
  • Connects to clinic_master_db (configured via .env: MASTER_DB_DATABASE)
  • Used by: ResolveTenant, TenantController, SuperAdminAuthController

④ TenantDatabase.php — Per-Tenant Connections

Located at: app/Core/TenantDatabase.php

  • Singleton-per-tenant — cached in static $instances['apollo_clinic']
  • DB name convention: clinic_tenant_{tenant_code}_db
  • If credentials aren't passed, it looks them up from master DB
  • Provides: fetch(), fetchAll(), insert(), execute(), query()

⑤ TenantRegistry.php — Global Tenant Code

Located at: app/Core/TenantRegistry.php

Simple static class — acts as a global variable for the current request's tenant code:

TenantRegistry::set("apollo_clinic")   ← called by ResolveTenant middleware
TenantRegistry::getCode()              ← called by tenant_db() helper

⑥ ResolveTenant.php — The Gatekeeper Middleware

Located at: app/Core/Middleware/ResolveTenant.php

Runs before every tenant-scoped endpoint. Does 5 things:

  1. Reads X-Tenant-ID header
  2. Queries master DB for tenant credentials
  3. Validates status and subscription
  4. Creates PDO connection to tenant DB
  5. Sets TenantRegistry and request attributes

⑦ functions.php — tenant_db() Helper

Located at: app/Helpers/functions.php

The bridge between models and the database. Every model calls this instead of manually managing connections.

8. Complete Request Lifecycle

    │
    ▼
index.php bootstraps → Router loads routes → matches /api/patients (POST)
    │
    ▼
Middleware pipeline runs in order:
    │
    ├─ 1. ResolveTenant  →  reads "apollo_clinic" from header
    │       ├── queries clinic_master_db.tenants for DB credentials
    │       ├── validates status = "active", subscription not expired
    │       ├── creates PDO to clinic_tenant_apollo_clinic_db
    │       └── sets TenantRegistry::$tenantCode = "apollo_clinic"
    │
    ├─ 2. AuthJWT  →  validates Bearer token, extracts user_id + role
    │
    ├─ 3. CsrfGuard  →  validates X-CSRF-TOKEN matches session
    │
    └─ 4. AuthorizeRole  →  checks user has 'Admin' or 'Provider' role
    │
    ▼
PatientController->store()
    │
    ├── calls $this->getAuthUser()  →  gets user from JWT
    ├── calls $this->getTenantId()  →  gets tenant_id from request attribute
    ├── validates input fields
    ├── encrypts sensitive fields (CryptoService::encrypt)
    │
    └── calls PatientModel->create($data)
            │
            └── $this->db()         →  tenant_db()
                    │
                    └── TenantRegistry::getCode()  →  "apollo_clinic"
                            │

                                    │

                                            │
                                            └── INSERT INTO patients (...) VALUES (...)

📌 Key Takeaway

Tenant isolation is enforced at three levels: (1) the application layer via middleware gating and per-tenant PDO singletons, (2) the database layer via separate MySQL databases per tenant, and (3) the MySQL user layer via GRANT permissions scoped to each tenant's database only. Even if application code had a bug, the MySQL user for Tenant A literally cannot query Tenant B's database.
